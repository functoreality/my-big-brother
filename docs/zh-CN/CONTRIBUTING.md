# 文档先行的协作流程

[English](../../CONTRIBUTING.md) | 简体中文

修改实现前，先确定已达成共识的产品与技术约定。
建议、实验成功或现有代码，都不能批准修改约定。
此规则适用于贡献者、主 Agent 和子 Agent，也覆盖任务提示词及安装指令。
先读[文档地图](README.md)、[PRD](REQUIREMENTS.md)和[技术总览](ARCHITECTURE.md)。
总览必须概括当前行为与方案，细节才交给链接，不能靠跳转才能理解系统全貌。

## 1. 修改实现前先分类

| 工作类型 | 首先可以做什么 | 何时可以改实现 |
| --- | --- | --- |
| 不改变含义的文档修正 | 修文字、翻译或导航 | 本身不授权代码变更 |
| 实现已经确认的约定 | 标明准确的 PRD、技术和细节章节，以及已授权任务 | 实现这些约定，保留其他行为 |
| 新行为、新技术策略或约定不明确 | 讨论问题，给出可评审的文档提案 | 明确同意后才能实施 |

修 bug 可以恢复已有文档中的不变量，不必凭空增加新需求。
先记录违反了哪条约定和复现方式，再实现修复。
重构可以保持既有设计。但不能借这两个名义增加未经确认的字段、依赖、保留项、
重试、锁、权限或兼容分支。若确实需要，进入第三条路线。

“实现”包括可执行 Markdown 任务、提示词、采集行为、校验器、默认配置和安装操作。
即使没有修改 Python，任务文字含义变化也可能改变运行行为。

## 2. 提出并评审文档变更

约定变化须先给出简短提案或准确的拟修改文档 diff，再改实现。
单独提案确有帮助时，可用 `docs/proposals/<topic>.md`。
不提前建立空的目录体系，也不为每处文字修正新增提案。提案说明：

- 用户问题、场景与现状。
- 拟改变的行为，以及涉及的 PRD、技术、细节章节。
- 哪些不变，尤其输入、输出、访问与保留范围。
- 相关替代方案、成本和失败情况。
- 验收例子与未定事项。

未同意的文字标为 **Proposed**，与现行约定分开。
Issue、README 计划项、子 Agent 建议、代码 diff、测试结果和 Git commit 都不等于批准。
在讨论或任务说明中记录用户/维护者的明确决定与批准范围，私人对话不必复制进公开仓库。

同意后，先更新现行文档，再实施。
用户行为改 PRD，技术策略改总览，准确接口与边界改所属细节约定。
总览中的概括和链接都要更新，不能让新行为仅存在于另一个提案里。

只批准提案的一部分时，只有这一部分成为现行约定，其他内容继续待议。
文档冲突或遗漏关键选择时，指出并询问，不能根据代码推定已经同意。

## 3. 按已确认范围实现

任务说明列出已确认章节、负责文件/组件、验收场景与待决事项。
等新决定时可以继续文档和隔离调查，不能先实现依赖该决定的内容，
也不能先装到真实环境来证明方案可行。

并行任务共享同一份现行约定，明确文件责任。
子 Agent 超范围的建议先报告，不能自我批准、扩大其他 Agent 任务，
也不能在方案尚未评审时改运行逻辑。

用满足约定的最小实现，不兼容或迁移未发布、已放弃的旧布局。
新增采集、输出、启动器先确认约定，再按[扩展指南](EXTENDING.md)落地。
私人资料与开发审计留在公开仓库之外。

## 4. 验证与交接

用隔离证据和临时目标做与改动相称的检查，覆盖受影响的例子和保持不变的约定。
测试验证已确认行为，不能反过来定义需求。
较大改动使用独立评审或空白上下文读者检查。
评审意见仍须对照约定判断，新建议回到步骤 2。
修复显著影响其他约定时再复评，小修明确恢复既有约定时不无限循环评审。

交接说明文档依据、行为改变、检查与重要限制。
区分单元/夹具、真实 Agent 解释、原生平台和实际定时触发。
Git 提交保持可评审，适合时先提交已确认文档，再提交实现。
提交顺序不能替代明确同意。

## 文档身份与职责

- **Current**：PRD、技术总览与领域约定描述现行共识。
  每条事实更新其所属文档，不复制第二份完整规范。
- **Proposed**：替代方案与未定事项不能指导实现。
  接受后把结论概括回现行文档。
- **Historical/evidence**：审计、开发记录和旧代码描述曾发生或验证的事情，
  不能覆盖当前需求。

PRD 定义用户结果和验收，技术总览定义实现手段与取舍，细节文档定义范围内的格式和协议。
下层细节会改变上层约定时，必须先评审对应变更。
用户指令优先，但依赖该指令的实现开始前，要先同步到相应文档。

英文是共享约定的规范版本。简体中文人类文档保持一致，使用相同的需求/章节编号。
翻译冲突是文档缺陷，不代表可任选另一种政策。
Agent 任务、JSON 字段和命令只有一份规范，公开 PRD 与技术总览不写私人路径。

## 开发基线

核心只用标准库，推荐 Python 3.11+。
不明显增加复杂度时，优先使用 Python 3.7 已有语法与标准库 API。
不只为写法新颖增加新版本要求，不经验证不宣称旧运行时兼容。
可选依赖按功能隔离。

测试使用合成隔离资料，不修改真实历史、shell/编辑器设置、定时任务或私人产物。

```sh
python -m unittest discover -s tests
```

简短的变更记录通常就足够：

```text
文档依据：PRD P…、技术总览 T…、细节章节…
决定：已有共识 / 明确批准的位置 / 仅提案
范围：具体行为变化与保持不变的约定
验证：相关场景、结果与未验证边界
```
