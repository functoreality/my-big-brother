# 扩展 My Big Brother

[English](../EXTENDING.md) | 简体中文

核心程序准备证据并管理一次复盘。
Agent 阅读 Markdown 任务说明，主导分析。
新增功能应放在对应的一侧，而不是把每一步语义分析都转成程序流程。

## 四个独立的扩展点

| 组件 | 职责 | 示例 |
| --- | --- | --- |
| 采集器 | 在宿主应用中记录活动 | Bash 钩子或未来的编辑器插件 |
| 输入适配器 | 读取记录，准备带索引的证据 | Codex JSONL 或 OpenCode SQLite |
| 分析任务 | 说明如何理解证据，以及希望得到什么结果 | 每日复盘或未来的每周复盘 |
| 分析器启动器 | 启动一个无人值守的 Agent | Codex CLI 或未来的其他后端 |

Codex 作为输入源，与 Codex 作为分析器启动后端，是两个独立的集成。
用户可以添加输入源，而不更换已选择的分析器。
较重的编辑器插件可以在独立仓库发布，
本仓库则维护它的输入适配器和集成说明。

## 添加输入

### 保存在源码之外的个人读取器

个人代码保存在 `C/readers/<source>/reader.py`，合成测试与必要说明放在旁边。
`C` 是 `python -m my_big_brother paths` 显示的配置目录，源码升级保留这些文件。
编辑 `C/config.json` 现有的 `sources` 对象，添加例如：

```json
"some_agent": {
  "enabled": true,
  "path": "/absolute/history/store",
  "reader": "/absolute/config/readers/some-agent/reader.py"
}
```

这是单个来源配置项，不是完整配置的替代文件。
来源名匹配 `[a-z][a-z0-9_-]*`。`path` 选择历史数据，`reader` 选择可执行 Python。
启用个人读取器时，两项都须为绝对路径，`required` 仍是可选布尔值。
`init --sources` 只列官方来源。仅使用个人来源时先运行 `init`，
再在分析前把生成的来源选择替换为明确的个人配置项。
已省略的来源不会被默认项重新合并回来，不需要注册或修改安装源码。

显式 `reader` 始终优先于同名官方实现，包括日后升级新增的官方支持。
文件缺失或损坏时报告 `unavailable`，按正常来源缺口和阻断规则处理，不静默回退。
`doctor` 只检查路径，不执行读取器。准备阶段只加载明确选中的代码，
以 Python 进程权限执行，不扫描目录、自动安装依赖或提供插件市场。

所选文件实现与官方读取器相同的接口：

```python
from datetime import datetime
from pathlib import Path
from my_big_brother.sources import SourceResult


def collect(path: Path, start: datetime, end: datetime) -> SourceResult:
    ...
```

建议保持单文件、使用绝对导入。运行时不把读取器所在文件夹加入 Python 导入搜索路径。
可选 `prepare_assets(rows, directory)` 使用现有素材准备接口。
准备阶段把所选路径和 SHA-256 存入日期内的 manifest 与上下文。
代码改变会使完成状态复用和旧运行发布失效，编辑后需重新准备。
摘要不跟踪间接依赖，加载不在读取器目录生成字节码缓存。
公共接口变化时个人代码可能需要维护。

新增同名官方支持时，用户同意前保持原绑定。
在相同窗口只读比较时间戳、角色、内容、缺口、个人过滤与复盘会话排除。
说明语义差异，不能只按条数判断。获同意后只删除 `reader` 绑定，
保留数据路径、启停、必需性与其他设置，旧代码先保留供回退。
不要把两种实现当成两个已启用来源重复读取同一份历史。

### 接口与上游贡献

给上游贡献时，在开发分支的 `my_big_brother/sources/` 中创建模块，实现：

```python
def collect(path: Path, start: datetime, end: datetime) -> SourceResult:
    ...
```

`SourceResult` 包含 `rows`、`status` 和 `gaps`。
状态使用 `ok`、`partial` 或 `unavailable`，
返回时间位于 `[start, end)` 内、按时间戳排序的记录。
记录是可序列化为 JSON 的字典，包含带 UTC 偏移的 ISO 时间戳，保留输入源特有字段。
会话记录应包含角色和内容。
通用准备逻辑把可读的内容摘录与精简索引分开保存。

在输入源选择代码中注册适配器，添加对应配置、任务输入规则和合成格式测试。
官方实现采用显式注册，个人实现则使用上面的文件绑定，不使用此注册表。
没有统一的活动数据结构。请说明支持的版本，并把解析失败表示为证据覆盖缺口。
测试合成夹具，经同意后只读验证已知真实会话的含义和复盘排除。
历史内容只是证据，不是指令。经用户同意才提供上游补丁，排除私人历史与本机绑定。

读取上游历史时，不要修改原始文件。
独立采集器通过 `C/raw-logs-path.txt` 或平台默认值选择根目录，
写入 `raw-logs/YYYY-MM-DD/<source>/`。它们不依赖 `storage.json`、
运行登记或 `results_root`，应保持路径选择简单。
Bash、Vim 和截图来源即使明确配置根路径，也必须采用日期/来源结构。
不要添加旧目录探测或迁移。

主项目的 `capture-path`、`record-screenshot` 等辅助命令直接写入自然日期路径，
不依赖登记表或永久运行状态。详见[存储说明](STORAGE.md)。
每份记录开始时确定日期和路径，之后保持位置不变。
不要因午夜或复盘分界而拆分 Bash、编辑器会话。
读取器必须能从较早启动日期下找到当前事件。
每张新截图是独立记录，使用自身拍摄日期，不使用守护进程的首次启动日期。

## 添加输出

对于基于同一天共享证据、时间线和任务划分的结果，
扩展每日任务的输出约定。
在核心程序中添加输出名称、稳定的保存路径和必要的校验。
复用已有的统一分析，不要为每种输出重新独立分析全部证据。

结构化输出需要说明数据格式，并进行有意义的校验。
供人阅读的输出需要清晰的内容边界和重跑规则。
应定义如何保留用户编辑，并避免重跑产生重复内容。

目的或时间范围不同的任务，可以使用自己的任务目录。
未来的每周复盘通常会读取已发布的每日记录，
而不是重新处理一整周的原始会话。

## 添加 Agent 启动入口

只有启动边界需要知道具体 Agent 的可执行文件、登录、沙箱和超时。
用共享的[自动化任务](../../tasks/daily-review/AUTOMATION.md)启动一次 Agent，
提供安装目录、Python、可选的明确日期，以及允许访问的位置。
由 Agent 自己调用通用准备、发布和回执校验，也完成已配置的后操作。
不要把 Agent 调用放进 `runner.py`、输入适配器、校验器或共享 CLI。
原生定时 Agent 可以直接使用相同任务，不需要额外启动器。

安装 Agent 可以根据本机执行接口编写入口，不确定时查询本机帮助或官方文档。
内置示例是 `python -m my_big_brother.analyzers.codex`。
新入口可保存在安装仓库之外，也可作为 PR 加入 `analyzers/`。
Codex 入口根据原始日志、结果与所选 profile 的目标准备写权限目录。
本机入口可用 `--write-dir /absolute/directory` 增加用户明确授权的目录。
启动前省略被已授权父目录覆盖的子目录，整体权限范围不变。
不能仅为缩短列表就授予未选定的共同父目录。
任务的输出绑定和后操作范围与这些文件系统授权分别保留。

入口只启动一次 Agent，传递必要的执行设置并保留日志。
日期规划、输入准备、发布和业务完成校验都由执行 Agent 负责。
有启动上下文时，Agent 自己调用 `begin-automation` 和 `complete-automation`。
内置 exec 入口返回的 `agent-exited` 只表示进程正常退出，
可选 tmux 模式返回 `session-started` 和同一交互会话的接入命令，两者都不代表业务完成。
Agent 写出的 `automation-result.json` 才记录经过校验的业务完成状态。
不要在每个入口里复制分析算法，或自动另启 Agent 执行后操作。

## 用户自定义任务

用户可以在 `C/local-tasks/` 保存 Markdown 指令，
不需要修改安装的标准任务。
程序不会隐式发现其中的文件。
明确选择的[个人配置档案](PROFILES.md)可以加载复盘规则、声明参考资料，
绑定输出和校验器，并配置单独限定范围的复盘后任务。
用户也可以直接把指令交给当前 Agent。
每个扩展都应定义输入、写入位置、权限和重试行为。

配置的任务可以维护长期知识、编辑用户指定文件或发送通知。
这类操作需要明确的目标和重跑规则。
不能因为报告重新生成，就再次发送相同通知。
应分别记录报告完成状态和后续操作状态。

需要稳定行为时，可以添加小型、确定性的辅助程序。
在有具体需求之前，不必先搭建通用任务框架。
